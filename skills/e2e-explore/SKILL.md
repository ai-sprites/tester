# Phase 1 — EXPLORE：探索并写计划

**输入：**本次需求或验收、实际改动、已有测试，以及可用的目标环境。

**输出：**项目已有位置的测试计划；无约定时可用 `docs/tester/<feature-id>/e2e-plan.md`。另一会话只读这份计划，就能判断哪些案例可以生成测试、每步做什么、预期是什么。

## 1. 读来源，查已有覆盖

读取请求、已确认验收、相关代码改动和已有测试；按需通过现有 Jira、文档或代码 MCP 读取工单与 PR，也可使用本地及用户材料，记录真实来源。按[项目适配](../e2e-workflow/references/repo-conventions.md)找到测试目录、配置、fixture 和命令，用项目支持的列举方式检查现有覆盖。

围绕本次变化列候选案例：正常结果、权限与上下文、功能开关、数据状态、错误、表单和持久化。只保留有行为价值的分支；源码帮助找分支和定位方式，预期仍以已确认验收为准。

## 2. 检查环境，打开目标应用

按[认证与环境](../e2e-workflow/references/auth-and-environment.md)核对服务可用性、登录、权限和测试数据，再按[探索工具](../e2e-workflow/references/exploration-tooling.md)选择浏览器能力。把核实后的准备方法与命令写入计划，后续阶段直接复用。

环境不通时记录失败现象和受影响案例，继续可独立完成的工作；不要换一个应用代替目标环境。

## 3. 探索需要确认的流程

沿用项目用例编号；没有约定时可用 `TC-n`。对不明确或高风险流程实际执行用户步骤，记录可见结果、定位方式、关键请求、就绪信号和数据。已有明确验收、步骤及数据的案例可直接进入生成，不要求逐个重复探索。服务器状态无法安全构造时，按[请求模拟](../e2e-workflow/references/request-mocking.md)使用范围明确的响应 patch，并观察目标分支确实出现。

每个案例使用准确的探索状态：

| Status | 含义 |
| --- | --- |
| `verified` | 在真实应用中执行了流程并观察结果 |
| `verified with mock` | 执行了流程，指定服务端响应被模拟；记录模拟范围和剩余集成风险 |
| `blocked` | 环境、权限或数据阻止探索；记录原因和下一步 |
| `unverified` | 尚未尝试，或范围、预期仍未确认 |

这些状态只代表探索证据。不能把源码推断写成已观察结果，也不能把探索成功写成自动化测试通过。

## 4. 解决缺项，写成独立计划

核对现有资料和已获答案，只把仍影响范围、预期或重要数据选择的问题交给用户决定。普通测试细节自行处理；答案写回正文，未解决项保留 `UNVERIFIED` 和所影响的 TC，不静默丢弃范围。

参考[计划模板](../e2e-workflow/references/plan-template.md)，沿用项目结构，写清目标、前置条件、用户步骤、可观察预期，以及必要的就绪信号、数据和 mock 理由。用例命名遵循项目约定；交接所需关键资料写入计划，不让生成依赖临时笔记。

保留已有用例 ID 和有效历史；失效案例注明已取消或替代及依据。探索状态依据真实观察，不能自动标成 `verified`。实现与验收冲突时保留冲突及来源，不能按实现反写预期。

## 5. 交接计划

列出验收、步骤和测试数据已明确的可生成案例；未探索、受阻或待定项保留真实状态与影响，不阻止明确案例继续。

需要将计划关联 Jira 时使用 [e2e-sync-test-cases](../e2e-sync-test-cases/SKILL.md)，沿用已有工单和测试记录；未要求回写则交付计划即可。同步受阻不阻止本地生成。

保留支持计划与问题判断的必要证据，只清理本次无用 scratch。

## 完成条件与下一阶段

- 来源、已有覆盖、项目运行方法和环境明确。
- 每个候选都有准确状态；步骤、预期和必要探索证据一致。
- 计划能独立使用，用例 ID、未覆盖项和阻碍清楚。

完整 E2E 任务继续 [Phase 2 — GENERATE](../e2e-generate/SKILL.md)。用户只要探索或计划时，交付计划与缺口，在此结束。
