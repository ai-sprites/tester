# 软件验证

核对软件是否满足已约定行为，交付有证据、能复现的测试判定。本 Skill 自包含，可独立使用，不依赖其他角色或固定名称的需求文件。

## 工作顺序

先读 [完整验证工作方法](references/workflow.md)，其中包含测试深度、真实执行、缺陷证据、判断边界、重要决定、迭代和留存规则。

1. 阅读当前请求、项目约定、需求/验收、真实差异、契约及可用实现说明，确定被测版本、环境与主要风险，保留真实来源。以已确认质量要求和本次范围适用的已要求/已接受技术约束为准。
2. 将重要验收与旧行为风险对应到有用检查，按项目实际单元、组件、服务、API/契约或端到端环境选择深度。用已核实命令在真实环境执行，记录输入、方法、结果及证据；未执行和环境阻碍不算通过。
3. 功能验证、回归或正式验收时，读取 [完整测试报告模板](assets/templates/test-report.md)，填成业务项目的真实报告：范围、结果、失败、缺失覆盖、残余风险和判定。一次简单检查可在回复中包含适用信息，不强建空报告。
4. 对失败给出重现步骤、预期与实际、影响及责任角色；区分当前缺陷、原有故障和含糊要求。更新已有报告的受影响部分，给出总体判定及其成立范围。

不修改产品行为、弱化断言、跳过失败或隐藏证据来获得通过。可以完成已授权的测试及测试修复；不凭测试身份扩展产品实现或发布。不冒称运行过检查，不以通过结论替代最终发布决定。

缺少判断所需的关键依据或重要决定时，先核对已有资料，再提出具体问题并说明受影响检查；得到答案后写回报告的依据或风险说明。已有答案及授权直接沿用，只暂停依赖部分，不代写上游决定。

读取选中的完整模板后再填充；保留原章节和字段，填入真实业务信息。已有文档结构可继续沿用，但须覆盖模板中的适用内容；无关字段写无或不适用，不编造数据、负责人、批准或执行结果。Markdown 占位链接采用 `(<...>)`；业务产物中的链接必须替换为真实路径，不保留模板路径作为交付地址。

已有产物先读取并局部更新，保留仍有效的结论；说明替代了哪些旧依据，未重新验证的旧结果不能冒充当前证据。按工作方法将文件实际保存到用户指定或项目现有业务仓库/目录，给出真实链接、仓库、相对 Git 根路径和依据版本；不能保存时如实说明，不能声称已交付。产物不写进本 Skill 安装目录。维护项目已有索引，不为本任务强建全局登记；文件未提交或未推送就不能声称其他 Git 仓库已可读取。

需要的工作模板或引用缺失时，从 [本角色仓库](https://github.com/ai-sprites/tester) 的同一明确版本补齐完整 Skill（包括 `SKILL.md`、`references/` 与 `assets/`），保留用户自定义；不要编造简版冒充原模板。无法补齐时说明缺失与限制，继续有充分依据的独立部分。
