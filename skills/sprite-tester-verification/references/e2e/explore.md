# 探索与计划

把验收与实际用户流程整理成另一会话可以直接据此生成测试的计划。

## 读取与预检

1. 读取请求、已有需求/验收、实际改动及相关测试；有工单或 PR 时读取真实来源，没有时明确写无。来源可以涉及前端、服务或全栈，不要求固定名称的需求文档。
2. 按[项目适配](project-conventions.md)找到测试配置、已有覆盖及可用命令，用项目支持的列举方式检查现有测试。明确相关权限、上下文、功能开关、数据状态、错误、表单及持久化分支，不凑固定案例数量。
3. 按[认证与环境](auth-and-environment.md)验证目标服务、登录和测试数据；按[探索工具](exploration-tooling.md)选择可用浏览器能力。网络、认证或环境受阻时记录真实原因，只暂停受影响用例，不用另一个应用替代目标。

## 探索候选用例

以 `TC-n` 记录候选案例，逐个执行真实用户步骤。记录可见结果、稳定定位方式、关键请求及就绪信号、需要的数据与权限。服务器状态无法安全构造时，按[请求模拟](request-mocking.md)使用范围明确的响应 patch，并证明目标分支确实出现。

探索状态与测试执行结果分开：

- `verified`：已在真实应用驱动该流程并观察结果。
- `verified with mock`：已驱动流程，但指定服务器响应被模拟；注明模拟范围和剩余集成风险。
- `blocked`：环境、权限或数据阻止探索，记录原因和下一步。
- `unverified`：尚未尝试，或预期/范围存在未确认信息。

源码和现有测试可以帮助找分支、接口、选择器，不能替代实际探索观察或充当已确认的验收。发现实现与验收冲突时记录冲突；不要按照当前实现反写预期。

需要用户决定范围、预期或重要测试数据选择时，先核对现有资料与已有答案，只问仍影响工作的缺项；使用当前客户端可用的提问能力或直接提问，不绑定工具名称。普通测试细节自行处理。未答复的部分保留 `UNVERIFIED` 与受影响案例，继续独立工作；不静默丢弃范围。

## 写入并交接计划

读取[完整计划模板](../../assets/templates/e2e-plan.md)，保存到 `docs/tester/<feature-id>/e2e-plan.md`。每个案例有一行和一个详情块，填写真实目标 spec 路径、setup、用户步骤、逐条 `expect:`、定位方式、端点、就绪信号、测试数据与 mock 理由。标题语言与命名服从目标项目，不强制英文 `should`。

保持 `TC-n` 不变，新 ID 高于包括 obsolete 行在内的历史最大值；删除需求时保留旧行并标 `obsolete`，记录依据。旧计划缺少状态字段时依据真实证据补齐，不能自动当作 verified。关键资料直接写入计划，不让生成阶段依赖探索对话或临时文件。

新计划没有真实来源工单时，`Sync target` 写 `none`，两个同步映射写 `N/A`，不发现或调用工单工具。有来源但未要求同步时也可保持关闭。已有同步身份、key 或旧 `Jira Test Cases Sub-task` 字段时，先按[远端同步](sync-test-cases.md)兼容读取并保留；缺字段、断连或暂停不能清空映射。需要同步时转入该流程预览和处理授权；同步受阻不阻止已有明确计划的本地生成。

## 完成检查

- 已有覆盖、范围、真实来源和被测环境明确。
- 每个候选都有准确的探索状态；未确认和未覆盖部分留在计划中。
- active 行的详情、步骤、预期与表格一致，生成范围可独立判断。
- 同步状态准确；保留必要证据，清理本次无用 scratch。
