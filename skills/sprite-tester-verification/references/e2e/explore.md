# Phase 1 — EXPLORE：探索并写计划

**输入：**本次需求或验收、实际改动、已有测试，以及可用的目标环境。

**输出：**`docs/tester/<feature-id>/e2e-plan.md`。另一会话只读这份计划，就能判断哪些案例可以生成测试、每步做什么、预期是什么。

## 1. 读来源，查已有覆盖

读取请求、已确认验收、相关代码改动和已有测试；有工单或 PR 时读取真实来源，没有则注明无。按[项目适配](project-conventions.md)找到测试目录、配置、fixture 和命令，用项目支持的列举方式检查现有覆盖。

围绕本次变化列候选案例：正常结果、权限与上下文、功能开关、数据状态、错误、表单和持久化。只保留有行为价值的分支；源码帮助找分支和定位方式，预期仍以已确认验收为准。

## 2. 检查环境，打开目标应用

按[认证与环境](auth-and-environment.md)核对服务可用性、登录、权限和测试数据，再按[探索工具](exploration-tooling.md)选择浏览器能力。把核实后的准备方法与命令写入计划，后续阶段直接复用。

环境不通时记录失败现象和受影响案例，继续可独立完成的工作；不要换一个应用代替目标环境。

## 3. 逐个尝试候选案例

以 `TC-n` 编号，实际执行用户步骤，记录可见结果、稳定定位方式、关键请求、就绪信号和所需数据。服务器状态无法安全构造时，按[请求模拟](request-mocking.md)使用范围明确的响应 patch，并观察目标分支确实出现。

每个案例使用准确的探索状态：

| Status | 含义 |
| --- | --- |
| `verified` | 在真实应用中执行了流程并观察结果 |
| `verified with mock` | 执行了流程，指定服务端响应被模拟；记录模拟范围和剩余集成风险 |
| `blocked` | 环境、权限或数据阻止探索；记录原因和下一步 |
| `unverified` | 尚未尝试，或范围、预期仍未确认 |

这些状态只代表探索证据。不能把源码推断写成已观察结果，也不能把探索成功写成自动化测试通过。

## 4. 解决缺项，写成独立计划

核对现有资料和已获答案，只把仍影响范围、预期或重要数据选择的问题交给用户决定。普通测试细节自行处理；答案写回正文，未解决项保留 `UNVERIFIED` 和所影响的 TC，不静默丢弃范围。

读取[完整计划模板](../../assets/templates/e2e-plan.md)。每个案例写一行和一个详情块，包含目标 spec、setup、用户步骤、逐条 `expect:`、定位方式、端点、就绪信号、数据及 mock 理由。标题沿用项目语言和命名方式；关键资料直接写入计划，生成阶段不依赖探索对话或临时笔记。

保持 `TC-n` 稳定，新 ID 高于历史最大值。失效案例保留旧行和详情，标 `Lifecycle: obsolete` 并注明依据；其余使用 `active`。旧计划缺少状态字段时按真实证据补齐，不能自动标成 `verified`。实现与验收冲突时保留冲突及来源，不能按实现反写预期。

## 5. 交接计划

列出可生成的案例：`active` 且 `verified` / `verified with mock`。其余案例保留在计划与覆盖缺口中，不阻止明确案例继续。

按需转入 [Phase 1.5 — SYNC](sync-test-cases.md)；无真实来源工单的新计划跳过此步，已有同步映射保留并兼容读取原 `Sources` 或旧 `Jira Test Cases Sub-task` 字段，同步受阻不阻止本地生成。

保留支持计划与问题判断的必要证据，只清理本次无用 scratch。

## 完成条件与下一阶段

- 来源、已有覆盖、项目运行方法和环境明确。
- 每个候选都有准确状态；表格、详情、步骤和预期一致。
- 计划能独立使用，稳定 ID、未覆盖项、阻碍及同步状态完整。

完整 E2E 任务继续 [Phase 2 — GENERATE](generate.md)。用户只要探索或计划时，交付计划与缺口，在此结束。
