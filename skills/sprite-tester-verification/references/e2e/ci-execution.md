# 独立执行、稳定性验证与 CI

生成或修复 E2E 后按本文件执行；分析 CI 失败时先取得同一版本的真实报告。命令和产物规则来自 [项目约定](project-conventions.md)，不假定包管理器、分支、定时器、浏览器矩阵、worker 数或报告命名。入口见 [E2E 工作流](workflow.md)。

## 本地完成口径

对新增或修复 E2E 默认执行以下验证，项目已有更严格要求时沿用：

1. 核对本次计划、spec 和目标版本；用项目支持的发现/筛选机制确认实际会运行的用例及 setup/teardown。
2. **目标测试隔离运行两次，关闭 runner retries。** 可用已核实 runner 的 repeat 机制，也可分别执行两次；两次均需真正执行目标测试并成功，跳过、零测试、只在 retry 中通过都不满足。
3. **关闭 retries 运行一次相关测试组。** 按 fixture、共享状态、功能或目录边界选择最能暴露回归与泄漏的组，并说明范围。若现有入口无法关闭重试，保留该次实际结果、首次失败及 flaky，明确这项无重试稳定性检查尚未满足；不能只引用最终汇总绿灯当作完成。
4. 运行适用且已配置的格式、静态检查或其他必要验证，不引入项目未采用的检查器。完成后核对变更与产物，清理本次 scratch。

使用 Playwright 且项目确认支持直接传参时，可据实际执行入口、路径和项目名使用 `--repeat-each=2 --retries=0` 完成目标隔离重复。现有 script 可能固定参数或需要额外的参数转发分隔符；先检查 script，不直接复制示例形成错误命令。

完整套件由项目既有 CI 或已授权执行流程负责，不要求每次修改都在本地跑全量。若两次隔离、相关组或 CI 中某部分受阻，记录受阻的具体命令、原因和未覆盖范围；已完成部分继续有效，但不能声称全部完成。通过后不无理由反复加跑；新变化、失败或未解决风险才需要追加验证。

## CI 的可重复性

提交的测试必须由 CI 的独立测试 runner 运行，能够通过项目配置准备环境、认证和测试数据；执行不依赖 AI 会话、MCP 浏览器、人工保留的登录窗口或探索 scratch。CI 的现有触发、分片、并发、重试与矩阵由真实配置决定，不能把本工作流的存在当作已经创建了调度或 CI pipeline。

保留 runner 的首次失败、重试与最终结果。重试成功是 flaky 证据，不是“未发生失败”。本地与 CI 不一致时比较版本、依赖、环境、认证、数据、并发、浏览器和实际命令，再定位时序；不要直接加 timeout、retry 或单 worker 来掩盖原因。

需要修改 CI 时只完成当前测试任务已授权且必要的调整，不因迁入文档擅自新增定时任务、外部通知、凭据或部署步骤。

## 报告与证据

从实际 CI run 取得对应的测试报告、日志、trace 和截图，记录 run 标识/链接、commit、目标环境、命令、结果及首次失败。用已安装框架支持的报告/trace 查看器读取，不预设 artifact 名或它必定可下载。

工程工具中间输出保持原配置；交付结论所依赖的必要附件经脱敏后保存到 `docs/tester/<feature-id>/` 并以真实相对链接引用。下载不到、受权限限制或只能外部查看的证据，写明真实来源和限制，不能伪称已落盘。

测试报告按通过、失败、未运行、环境阻碍分别记录，每项结论只能覆盖实际运行的版本与范围。失败处理见 [修复失败](heal.md)，时序排查见 [可靠性与就绪信号](reliability-and-readiness.md)。
