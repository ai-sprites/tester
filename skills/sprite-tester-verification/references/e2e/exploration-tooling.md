# 实时探索与工具回退

探索用于确认用户步骤、分支和可见结果，并发现可重复的测试信号。它提供计划依据，不能代替独立 runner 的测试通过证据。阶段入口见 [E2E 工作流](workflow.md)。

## 选择可用工具

先发现当前客户端实际提供的浏览器能力及使用方式。可使用浏览器连接器、MCP、受支持的 UI 工具或项目 runner；不要求安装固定浏览器插件，不假设某个工具名、版本或调用 schema 存在。

在投入具体流程前确认浏览器能访问被测地址、认证可用、所在网络与仓库环境是否一致，以及工具是否能读取项目需要的文件。浏览器沙箱可能没有仓库文件、私有 DNS 或模块加载能力。文件访问拒绝、DNS 失败、模块不可加载说明这条工具路径受限，不能据此断定产品失败，更不能尝试绕过访问边界。

按问题选择证据：页面结构、控件名称和状态适合可访问性快照；布局、遮挡、渲染异常需要截图。记录实际观察到的 hooks、数据条件和请求，不凭工具中的猜测补写结果。

## 回退到项目 runner

仓库测试可运行而交互浏览器受限时，可以创建一次性 probe spec：

1. 确认 runner 的发现规则和显式运行方式，选择已有忽略 scratch 目录或安全临时位置；不要假定任意临时路径都会被框架发现。
2. 复用目标项目自己的 fixture、认证和辅助层，运行最小用户流程，只采集计划所需的页面状态、请求或结果。
3. 输出不包含凭据、敏感表单值或完整认证状态。将确实需要留存的观察转为脱敏证据，记录为探索结果。
4. 保存本次创建文件的清单，完成后仅清理这些文件；原有 scratch、用户修改和既有证据保持原状。

也可使用已安装 runner 支持的 debug、codegen 或 trace 功能。先核对当前安装版本、配置和帮助；不要因示例中的版本限制擅自升级框架或修改客户端配置。录制代码只是候选步骤，还需按 [生成阶段](generate.md) 转为独立、稳定的测试。

## 受阻时如何交接

真实流程和合理回退均不可用时，将受影响用例标为 `blocked`，写明已经尝试的工具、失败点和缺少的访问或条件；尚未尝试或预期未确认的用例保持 `unverified`。源码分析可以支持风险和候选步骤，不能把两类用例改成 `verified`。

其他已验证用例可以继续，是否移除必要覆盖取决于已有验收和明确的范围决定。不要因为工具受限而默默删除计划项，也不要反复询问已经确定的条件。正式计划与必要探索证据保存到 `docs/tester/<feature-id>/`；一次性输出不能提交为“测试通过”。

状态安排见 [探索阶段](explore.md)；服务端分支见 [响应模拟](request-mocking.md)。
