# 可靠性与就绪信号

生成 spec 和修复失败前读取。以下是排查线索，不是穷尽分类；不匹配这些症状时继续检查断言逻辑、数据、配置、依赖和应用行为，不能直接宣判产品或环境有错。入口见 [E2E 工作流](workflow.md)。

## 每次交互的顺序

按 `arrange → arm → act → await → assert` 安排有异步依赖的步骤：

1. **准备：**先设置认证、上下文、测试数据和 route，再触发依赖它们的导航或操作。
2. **订阅：**在触发事件前创建请求/响应等待 promise；不能先 `await` 一个尚未触发的响应，也不能点击后才开始订阅。
3. **操作：**执行计划中的用户动作。
4. **等待：**等待已经订阅的具体事件和必要的 loading 结束信号。
5. **断言：**用可重试的界面断言核对这次操作的结果。响应到达不代表 DOM 已更新，旧内容可见也不代表新结果已呈现。

每个步骤只选择实际需要的信号；纯 UI 操作不必捏造网络等待。网络等待按已知 URL/路径、method、预期 status 及必要的请求参数/实体身份筛选，避免捕获同一路径上另一次请求。错误分支要匹配该分支的预期状态，不能统一等待成功响应。多个独立信号应先全部订阅，再操作并共同等待。

不以固定时长判断就绪，不新增 `waitForTimeout` 或 `networkidle` 等待来恢复绿色结果；轮询、动画和环境负载会让它们失真。已有调用按本次受影响范围处理，不照抄为模式，也不借机重写无关代码。缺少真实信号时记录缺口并定位原因，不编造等待。

## 例：等待本次搜索的响应与结果

以下仅演示顺序；端点、参数、控件和结果必须来自当前计划。若操作会触发多个同类请求，继续收窄请求身份。

```ts
// arrange：认证、测试数据与必要 route 已准备好，目标结果尚未出现
const result = page.getByRole("link", { name: "Example result", exact: true });
await expect(result).toBeHidden();
// arm：先订阅本次请求，再执行触发动作
const response = page.waitForResponse((res) => {
  const url = new URL(res.url());
  return url.pathname === "/api/search"
    && url.searchParams.get("q") === "example"
    && res.request().method() === "GET"
    && res.status() === 200;
});

// act
await page.getByRole("searchbox").fill("example");
await page.getByRole("button", { name: "Search", exact: true }).click();
// await：响应完成还不代表界面已更新
await response;
// assert：确认本次查询对应的实际结果
await expect(result).toBeVisible();
```

## 常见失败与处理

| 症状或类别 | 应核对的原因 | 修复与验证重点 |
| --- | --- | --- |
| 偶发通过/失败 | 时序、共享数据、上下文泄漏、环境或外部依赖波动 | 找到可观察原因；独立数据与上下文，显式就绪信号；记录首次失败和每次执行，重试通过仍是 flaky |
| 竞态 | 订阅晚于操作、多个请求顺序不确定、等待匹配过宽 | 先订阅后操作；收窄请求身份并等待真正依赖的结果，不能用全流重试补救 |
| 陈旧引用或错行 | 缓存 ElementHandle、刷新后复用旧索引、旧内容满足断言 | 使用 Locator 与稳定实体身份，确认本轮数据已经呈现；Locator 可重复使用，缓存句柄不可冒充它 |
| DOM 脱离 | 列表或弹层在操作期间卸载、重新创建 | 使用能重新查询的定位和正常 actionability；自定义事件前确认目标已附着且状态就绪，不用强制点击越过缺陷 |
| 动画/过渡 | 操作或断言落在中间态 | 等待可操作或最终可见状态；淡出用隐藏断言，不用猜动画时长或无关 transform/opacity 值 |
| API 延迟或旧界面 | 页面壳先出现、请求完成后尚未渲染、上一次结果仍可见 | 等具体响应、必要 loading 消失和本轮结果；不要等待全部网络闲置 |
| 防抖/节流 | 输入完成时请求还未发出、提交动作未执行 | 输入前订阅目标请求；使用产品真正的提交动作；仅在行为需要逐键输入时模拟逐键输入 |
| mock 时序或命中错误 | route 安装太晚、匹配过宽、响应结构变更、断言对真实数据也会通过 | 提前安装窄 route，证明它被命中，等待 mock 数据呈现并断言区别于原始状态的结果 |

验证“没有发请求”不能只看某一瞬间的计数。必须在动作前开始观察，定义有行为依据的观察边界并等待操作完成；若无法确定边界，将证明能力的限制写入计划，不把任意短暂停顿当作可靠断言。

## 修改边界与完成证据

修复要保留验收意图和有效断言。不能删断言、改成宽泛 truthy、吞掉异常、自动添加 `skip`/`fixme` 或提高重试次数来获得通过。增加 timeout 只有在可证实的项目时限或操作预算确需调整时才有依据，不能代替时序诊断。确认是产品缺陷时保留失败证据并按 [修复失败](heal.md) 交接；不擅自把失败移出验收范围。

新增或修复的 E2E 默认需要**目标测试隔离运行两次且关闭 retries，再运行一次相关测试组**。具体命令、测试组边界及已有更严格要求按 [CI 与执行](ci-execution.md) 核实。稳定性验证通过不抹掉此前失败；无法完成的部分明确记录未执行或阻碍，不能算作通过。

测试数据应能独立准备，各测试不依赖执行顺序；通过相关测试组有助于发现状态泄漏，但不能证明所有并发组合都安全。CI 的并发、浏览器和数据隔离要求仍按目标项目执行。

响应补丁细节见 [响应模拟](request-mocking.md)；定位原则见 [选择器与控件断言](selectors-and-locators.md)。
