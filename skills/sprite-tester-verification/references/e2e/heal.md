# 失败诊断与修复

目标是找出并验证真实原因。结果可以是修复后的测试、产品缺陷、环境阻碍、需求冲突或尚待调查；不能把所有失败强塞进固定分类。

## 先收集证据

读取失败命令、版本、环境、计划 TC、具体步骤、错误信息和 runner 产物。CI 问题按[CI 执行](ci-execution.md)取得真实 report/trace；缺失就说明，不能声称看过。

先按[认证与环境](auth-and-environment.md)检查目标服务、网络、会话和测试数据。仅在证据显示会话过期时执行项目既有登录准备；不要照搬固定 health endpoint 或登录 project。环境受阻仅暂停依赖部分。

| 症状 | 要核对的证据 |
| --- | --- |
| 定位不到或定位到多个控件 | trace 中 DOM、可访问名称、项目 test ID 配置和最近 UI 改动 |
| 单独通过、成组失败 | 数据、权限上下文、storage、route/监听器清理及执行顺序 |
| 文本或输入断言失败 | 已确认要求、真实控件状态和项目文案来源 |
| 4xx/5xx 或返回形状变化 | 请求、响应、fixture 数据、认证与接口契约，区分产品错误和测试前置错误 |
| 只在慢机器/CI 失败 | 具体就绪信号、arm-before-act 顺序、动画及 debounce |
| 重试后通过 | 首次失败及次数，按 flaky 保留，不当作稳定通过 |

## 修改依据

结合[可靠性与就绪信号](reliability-and-readiness.md)的八类常见问题判断时序、隔离、mock 和定位缺陷；同时检查测试逻辑、错误预期、配置及环境。证据不足时继续缩小复现范围并标明未知。

在授权范围内修正测试、POM/辅助层、fixture 或等待顺序，复用真实契约。不可通过 `waitForTimeout`、`networkidle`、宽泛断言、吞错、额外 retries 或删除失败断言来恢复绿色。不用 mock 覆盖本应验证的真实集成问题。

## 测试正确而产品错误

保持已确认预期，报告 TC、计划步骤、预期/实际、最小复现、影响、缺陷链接（若有）及证据。测试角色不自行改产品行为，不因用户要求“修测试”就改验收。

默认保留失败测试。只有项目已有隔离规则或用户明确授权适用于此缺陷时，才使用 `fixme`/skip 等临时隔离；记录原因、真实追踪依据和恢复条件，并在报告标为未通过/未覆盖。不能把隔离后的套件绿色算作该案例通过。没有 issue 时不编造编号，也不擅自创建远端缺陷或发送评论。

## 修复验证

按[生成阶段的验证要求](generate.md)关闭重试后两次隔离运行、一次相关测试组运行，并完成适用的项目检查。无法执行的部分记录具体阻碍；不把无代码变更的重复重跑当作修复。

把修复前后证据、原因、实际结果和剩余风险写回 `docs/tester/<feature-id>/verification.md`，必要附件整理到 `evidence/`。计划确实需要改变时保留身份及有效历史，按已有同步配置处理差异。
