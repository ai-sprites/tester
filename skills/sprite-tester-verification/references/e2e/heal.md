# 失败分支 — HEAL：诊断并修复

**输入：**失败的测试、运行命令及本地或 CI 的失败证据；有关联计划时同时读取对应 TC。

**输出：**有证据的原因和处理结果：测试修复、产品缺陷、环境阻碍、需求冲突或尚待调查。测试修复回到 [Phase 3 — EXECUTE](ci-execution.md) 验证。

## 1. 还原失败，检查环境

读取失败版本、环境、命令、出错步骤和错误信息。有关联计划就核对 TC；没有计划时，用现有测试及已确认验收核对预期，不为诊断强建计划。预期依据不明时只暂停依赖该预期的修改，仍可诊断环境和执行问题。CI 问题按[执行阶段](ci-execution.md)取得真实 report/trace；缺失的证据明确记为缺失。

按[认证与环境](auth-and-environment.md)检查目标服务、网络、会话和数据。证据显示会话过期时，运行项目既有登录准备；环境受阻时只暂停依赖部分。

## 2. 用证据缩小原因

| 症状 | 优先检查 |
| --- | --- |
| 定位不到或命中多个控件 | trace 中 DOM、可访问名称、test ID 配置与最近 UI 改动 |
| 单独通过、成组失败 | 数据、权限上下文、storage、route/监听器清理及执行顺序 |
| 文本或输入断言失败 | 已确认要求、真实控件状态和项目文案来源 |
| 4xx/5xx 或响应形状变化 | 请求、响应、fixture 数据、认证与接口契约 |
| 只在慢机器/CI 失败 | 就绪信号、arm-before-act 顺序、动画和 debounce |
| 重试后通过 | 首次失败及发生次数；按 flaky 保留，不算稳定通过 |

结合[可靠性与就绪信号](reliability-and-readiness.md)的八类常见问题检查时序、隔离、mock 和定位，同时核对测试逻辑、预期、配置及环境。证据不足时缩小复现范围，保留未知，不强行归类。

## 3. 处理根因

在任务授权内修正测试、POM/辅助层、fixture 或等待顺序，复用真实契约。修复须解释原失败，不能用 `waitForTimeout`、`networkidle`、宽泛断言、吞错、额外 retries 或删除断言恢复绿色；不能用 mock 遮住本应验证的集成问题。

测试符合已确认预期而产品错误时，保留预期和失败测试，记录 TC/计划步骤（若有）、失败测试与步骤、预期/实际、最小复现、影响、真实缺陷链接（若有）及证据。修测试的请求不授权修改产品行为或验收。

临时 `fixme`/skip 仅按项目已有隔离规则或明确授权处理，记录追踪依据和恢复条件，在报告中标为未通过/未覆盖。隔离后的套件绿色不代表该案例通过；没有工单时不编编号、不擅自创建远端事项或发送评论。

## 4. 回到执行阶段验证

修复后回 [Phase 3 — EXECUTE](ci-execution.md)，按其统一要求完成正式运行与项目检查。没有代码或环境变化的重复重跑，不算修复。

把修复前后证据、原因、实际结果和剩余风险写回 `docs/tester/<feature-id>/verification.md`，必要附件放在 `evidence/`。环境或依据仍受阻时记录确切缺项和下一步。计划确需改变时保留身份与有效历史，按已有同步配置处理差异。

## 完成条件与下一阶段

- 每个失败都有证据支持的原因，或明确的未知、阻碍和下一步。
- 测试修复已返回 Phase 3 验证，报告包含实际执行结果。
- 产品缺陷、需求冲突和未通过案例仍清楚可见，没有用隔离或重跑冒充通过。

继续处理执行阶段剩余失败；没有可继续的检查时，交付报告与尚未完成部分。
