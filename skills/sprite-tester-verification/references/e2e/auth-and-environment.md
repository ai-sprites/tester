# 认证、环境与测试数据

探索前和排查环境类失败时读取。先按 [项目约定](project-conventions.md) 发现真实配置，不假定项目采用某套 SSO、二次验证、环境变量或登录项目。入口见 [E2E 工作流](workflow.md)。

## 环境预检

1. 确认本次允许使用的应用环境、被测版本、账号角色和数据范围。复用已有配置；只有项目确实需要且目标文件不存在时才从它的样例生成本地配置，不覆盖已填写内容。
2. 使用项目定义的服务健康检查或等效可用性检查，核对预期响应。不是每个应用都有健康端点，也不是每个合法响应都是 `200`；不要猜路径或拿其他应用替代被测系统。
3. 用已发现的测试列举或配置检查命令确认配置能加载、目标测试可发现，并识别会运行的 setup/teardown。浏览器能打开页面不等于仓库 runner 已可运行，反之亦然。
4. 需要认证时沿用现有 fixture、setup 或项目登录流程。确认认证状态属于正确环境、账号和有效期，并验证受保护页面确实可访问；出现重定向或未登录提示时，先诊断会话再重新认证。

DNS、网络、访问权限或服务故障只阻碍依赖该环境的检查。记录失败的检查与现象，继续已有充分依据的计划、源码核对和其他独立检查；不把这些工作声称为受阻流程的执行证据。

## 会话与隔离

- 从 runner 配置确认存储状态的真实路径、读取时点、上下文继承关系和清理责任。不要把另一个账号或环境的缓存状态当作默认会话。
- 会话、租户/组织、权限、语言或其他影响行为的上下文，应在触发业务请求前准备好。测试间不能依赖前一个用例留下的浏览器状态。
- 使用当前任务授权的数据准备和恢复方法。共享数据的修改、具有外部副作用的流程，应明确隔离范围和清理方式；不能把真实环境重置或权限变更当成普通测试准备。
- 无法安全构造的服务端状态可按 [响应模拟](request-mocking.md) 处理；浏览器内的模拟只能证明对应客户端行为，不能证明真实服务端权限和持久化正确。

## 秘密与证据

认证文件、本地配置和包源凭据是否被忽略，应实际检查，不能把文档中的“已忽略”当事实。不要提交或打印密码、令牌、二次验证种子、会话 cookie 和 storage state，也不要将其写入步骤标题、命令参数展示或报告。

日志、URL、请求与响应、截图和 trace 都可能携带秘密或用户数据。先按实际内容脱敏，再将必要证据留存在 `docs/tester/<feature-id>/`；保留能定位问题的状态、步骤和错误信息，不能用“脱敏”删除失败事实。无法安全导出的原始产物说明访问位置和限制，不虚构已归档附件。

浏览器和仓库环境不一致时见 [探索工具](exploration-tooling.md)；CI 中重复故障见 [修复失败](heal.md)。
