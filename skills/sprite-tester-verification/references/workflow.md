# 通用验证流程

用于功能验证、回归、验收或单次检查。浏览器探索、生成自动化测试和修复 E2E 时，直接使用 [E2E 工作流](e2e/workflow.md)。

## 1. 明确范围

**输入：**当前请求、项目约定、真实差异，以及已有的需求/验收、设计、契约、架构、开发方案和测试证据。

**步骤：**

- 核对被测版本、环境、关键输入、已确认行为和主要回归风险，保留资料的实际来源与版本。其他角色未安装、没有完整 PRD 或固定格式文档，不阻碍验收明确的检查。
- 区分已确认要求、实现现状和待定建议；不能按当前实现反写验收。资料缺失、冲突或含糊时，注明来源、影响和待确定项，只暂停依赖它的检查。
- 先查已有资料、答案和授权，再提出确实需要人的决定。说明具体问题、为何现在需要及影响；有真实选择时给 2–3 个互斥选项和取舍，合理推荐在前，否则直接询问缺失信息。使用当前客户端适用的提问方式，不要求安装工具。收到答案后写回依据和决定人/角色；建议、未答复与“待确定”不算同意。

**输出与完成：**检查范围、依据、环境和风险已明确，待确定项及其影响可辨认。测试角色不代写产品、设计或架构决定；普通测试细节自行处理，其余可独立工作继续。

## 2. 选择检查

**输入：**明确的验收、变更风险、项目已有测试及适用于本次范围的技术约束。

**步骤：**

- 将重要验收和旧行为风险对应到有用检查，按实际风险选择单元、组件、服务、API/契约或端到端深度。
- 覆盖本次相关的正常结果、失败、权限、空数据、兼容及回归。复用已有有效覆盖，不凑固定用例数量，不写仅复述实现的镜像测试。
- 从项目文件、CI 或已核实说明确认执行命令、环境和预期结果；无法执行的检查保留为缺口，不默默移出范围。

**输出与完成：**一份可执行的检查清单，每项能回答“验证哪个行为或风险、如何检查、预期是什么”。已有报告或测试可以承载清单，无须另建重复计划。

## 3. 实际执行

**输入：**检查清单、核实后的命令或操作、可用环境和测试数据。

**步骤：**

- 在授权环境中执行，记录版本、环境、关键输入、精确命令/方法与真实证据。结果分别标明通过、失败、未运行或环境受阻；未执行不算通过。
- 失败记录重现步骤、预期与实际、影响和证据，区分本次缺陷、项目既有故障与不明确要求。偶发失败保留条件、次数和首次失败，不能靠重复重跑隐藏问题。
- 已授权的测试及测试修复继续完成。新增或修正测试验证可观察行为，保持确定性和有效断言；不能通过改变产品行为、降低门槛、跳过失败或隐藏日志获得通过。修复后的结论以实际复验为准。

**输出与完成：**每项检查有真实状态；失败可复现或已说明复现限制，受阻项写明缺少的确切证据、访问或决定。保护用户工作、测试数据和秘密，不以测试身份扩展未授权的产品实现或发布。

## 4. 报告与交接

**输入：**检查结果、失败证据、未覆盖项和剩余风险。

**步骤：**

- 功能验证、回归或正式验收创建或更新[测试报告](../assets/templates/test-report.md)，按[交付与留存规则](delivery.md)保存。单次简单检查可在回复中包含适用信息，不强建空文档。
- 报告覆盖范围与依据、逐项结果、失败、缺失覆盖、残余风险和总体判定。判定为通过、失败或受阻，附理由与成立范围；部分通过不能代替整体结论。已发现的问题注明负责处理的人或角色；未知时如实说明，不编造责任人、风险或缺陷。
- 沿用旧报告仍有效的内容，只更新本次变化影响的部分，说明哪些依据或结论已替代、仍适用或需要重验。未复验的旧结果不能冒充当前证据，不因需求迭代重做全部角色的工作。
- 用白话先说结果、影响和需要决定的事，详略随任务调整，必要证据和判定不能省略。询问“已有成果”时盘点真实产物和缺口，不补写其他角色产物。

**输出与完成：**交付真实报告/证据链接，以及有明确范围的测试结论和后续处理项。通过只支持实际覆盖，不承诺无缺陷、资料语义完全一致或生产可以发布；产品范围、重要架构、实质风险接受和最终发布由有权的人决定。

快速迭代可减少重复流程和文档，不能降低验收责任、安全、隐私、合规、数据损失防护、共享或外部契约、迁移恢复及昂贵或难逆决定的标准。已发现风险说明影响、证据或未知，以及责任人或下一项检查；没有则写无或省略，不阻止无关工作。
